Off-axis projection

Run it yourself

This page is also an executable Jupyter notebook: open / download 06_offaxis_Projection.ipynb. The notebooks run end-to-end and double as part of Mera's test suite.

This page shows how to make maps of a simulation from any viewing direction, not only along the box axes x, y or z. Every map comes from one call:

projection(obj, var, unit; <view>, <framing>, <binning>, <pxsize>)

Compared with an axis-aligned map, only the viewing direction is new. center, range_unit, pxsize, weighting and units work the same way, so this page explains only what changes when the camera does not look along a box axis.

Gas and stars side by side. Every chapter uses the same camera on the gas and on the stars, because the keywords describe the camera, not the data. Where the two differ, the page says so. A star is a point without size, so :overlap and :exact fall back to :cic for stars (Chapter 7), a star map has no finest resolution (Chapter 1), slice does not work on stars (Chapter 12), and split does not exist for them (Chapter 5).

Data. AVALON AV05CD, output 390: 51.5 million cells on levels 6 to 12, a 48 kpc box, t = 580 Myr. It is not part of the public example data, so point the path at a run of your own or set MERA_AVALON.

One guarantee holds on the whole page: the mass on a map equals the mass of the data, to rounding error, at any angle, pixel size and kernel, as long as no frame cuts part of the data away (Chapter 3). The tests that check this are listed at the end of the page.

1. Your first off-axis view

A projection is a camera. The data never moves, only the camera does.

The camera looks along one line, the line of sight, los for short. The los vector points from the object toward the camera, so the camera looks along -los. Each pixel adds up one straight column through the data along that line. "Off-axis" means the line of sight is not one of the box axes x, y or z.

Am I off-axis at all?

callpath
direction=:x, :y, :zaxis-aligned. No camera is built, and m.los comes back empty
direction=:faceon, :edgeonoff-axis
los=, inclination=, azimuth=, theta=/phi=, position_angle=off-axis

Some quantities exist on only one of the two paths (Chapter 8), and the error message does not say which path a call took. Check m.los: it is empty on the axis-aligned path.

Two kinds of aim

  • You name the direction. los=[1,1,1], or direction=:x/:y/:z. Pure geometry, valid on any data whether or not there is an object in the box.
  • You ask Mera to find it. direction=:faceon/:edgeon, or axis=:angmom, read the orientation off the data's angular momentum. Convenient for a disc, an assumption everywhere else. Chapter 6.

This chapter starts with the first kind. Mera uses exactly the vector you give, so the view does not depend on the data or on center. The second kind computes the axis from the data about center, so a wrong center gives a wrong axis without any warning (Chapter 6).

# One map on physical axes: kpc, true aspect ratio, no smoothing between pixels.
function showmap!(ax, m, key; logscale=true, cmap=:inferno, crange=nothing, blank0=true)
    A = Float64.(m.maps[key])
    blank0 && (A = replace(A, 0.0 => NaN))   # empty pixels, whichever convention produced them
    A = logscale ? log10.(A) : A
    e = getextent(m, :kpc)
    xs = range(e[1], e[2], length=size(A,1))
    ys = range(e[3], e[4], length=size(A,2))
    hm = heatmap!(ax, xs, ys, A; colormap=cmap, nan_color=EMPTY_COLOUR, interpolate=false,
                  colorrange = crange === nothing ? Makie.automatic : crange)
    ax.aspect = DataAspect()
    return hm
end

# shared colour range across a set of maps (2nd percentile → max), so panels are comparable
function sharedrange(ms, key; logscale=true)
    v = reduce(vcat, [vec(Float64.(m.maps[key])) for m in ms])
    v = logscale ? log10.(filter(x -> x > 0, v)) : filter(isfinite, v)
    (quantile(v, 0.02), maximum(v))
end

A direction you chose

You give a vector, Mera builds a camera from it, and you can read the camera back from the map.

The second call looks along the box z axis. That is not an off-axis projection: it runs on Mera's axis-aligned path, which needs no camera because the image axes are the box axes. The printed lines show which path each call took.

# ONE window, reused by every chapter, so the only thing that changes between cells is the keyword

diag = projection(gas, :sd, :Msol_pc2; los=[1,1,1], win...)

A direction Mera works out for you

For a disc galaxy the view you usually want is along its spin axis, and direction=:faceon and :edgeon compute that from the data. They are a convenience, not a different mechanism: they end up as a los vector like the one above, and you can print it to see which one. Chapter 6 and the Auto-Frame page show more ways to find a galaxy's centre and orientation.

`:faceon` needs `center` on the object

:faceon/:edgeon and axis=:angmom derive the orientation from the angular momentum of the loaded data about center. center defaults to the box corner, and L about a corner is dominated by the lever arm of the whole box. You get a plausible-looking tilted galaxy, with no error and no warning. Always pass center=[:bc], or the object's own centre. Chapter 6 says what it sums over and how to check it; Chapter 8 gives the test that catches a wrong centre.

# The convenience form, in the same window as the two maps above. Print the line of sight it chose
# and compare it with the ones you typed: :faceon is a `los` you did not have to work out.
fo = projection(gas, :sd, :Msol_pc2; direction=:faceon, win...)
eo = projection(gas, :sd, :Msol_pc2; direction=:edgeon, win...)

Read the output back:

  • m.maps is a dict of 2-D arrays; m.maps[:sd] is the surface density in Msol_pc2.
  • getextent(m, :kpc) returns [xmin, xmax, ymin, ymax] in the image plane, the raw m.extent is in code units, so always convert.
  • m.los, m.up, m.cam_right are the camera basis the call actually used; m.direction reads :offaxis.

The los vector printed above is not a number you chose. It is the disc's angular momentum axis, computed from your data about your center. Aligning the camera with the net angular momentum of the disc is the standard way to define a simulated galaxy's own frame (Abadi et al. 2003). The viewing angle is then an explicit parameter of the image, and a chosen one (Torrey et al. 2015; Bottrell et al. 2017).

How fine to make the pixels

pxsize sets the pixel size, and it is the keyword that decides the run time. Measured on the machine that renders this page, at fov=16, with 4 threads and the default :overlap (with 8 threads the fine end runs 30 to 40 % faster):

pxsizemaptime
300 pc107²12.5 s
100 pc321²13.7 s
50 pc641²17.9 s
20 pc1601²103 s
11.7 pc, the finest cell in the run2731²452 s, 60 MB

The rule: compare the pixel with the cells. While a pixel is larger than the cells it covers, a finer pixel costs almost nothing, because most of the time goes into reading every cell once. Once the pixel is smaller than the cells, the cost rises fast. On this mesh that happens near 50 pc. On another mesh it happens elsewhere, so estimate it from your own lmax.

Why. :overlap spreads each cell over n³ sample points, with n = ⌈cell size / pixel⌉. While the pixel is larger than the cell, n is 1. Below that, the cost grows with the cube of the ratio: in the table, 300 to 100 pc costs 10 % more time, 100 to 20 pc eight times more.

Two chapters choose their own pixel on purpose: Chapter 7, where the ratio of pixel to cell is the experiment, and Chapter 11, where a star map is limited by the number of stars per pixel.

The mass on a gas map does not change with pxsize (Chapter 8). The line-of-sight velocity dispersion σ_LOS hardly changes on this galaxy, but that is not true in general, so Chapter 8 measures it. Choose pxsize for the image you want, and state it.

Modifiers, which combine with any of the above: up=, position_angle=, angle_unit=:deg (default) or :rad.

axis= takes :x, :y, :z, a 3-vector, or :angmom (alias :L). Combining it with direction=:faceon/:edgeon is an error, because those already use L.

How los becomes an image

Mera builds a right-handed orthonormal basis from los, and returns it on the map:

fieldis
m.losthe viewing direction, normalised
m.cam_rightimage x, the map's first index
m.upimage y, the map's second index

with cam_right x up = los.

Without up=, the camera uses world +z as its up hint, and +y when the line of sight is within 3 degrees of the z axis. Along the six box directions this gives:

losimage ximage ycompared with the axis-aligned map
[0,0,1]+x+ythe same orientation as direction=:z
[0,0,-1]-x+ydirection=:z mirrored left to right: seen from the other side
[1,0,0]+y+zthe same orientation as direction=:x
[-1,0,0]-y+zdirection=:x mirrored
[0,-1,0]+x+zthe same orientation as direction=:y
[0,1,0]-x+zdirection=:y mirrored
[1,1,1](-x+y)/√2(-x-y+2z)/√6no counterpart. Up is +z as seen across the line of sight

"The same orientation" means the image axes agree. The pixel grids still differ slightly, because the two paths place pixel edges differently.

Pass up= whenever that is not what you want. position_angle then rolls the image about the line of sight, leaving m.los alone.

Meanings

inclination is the angle between the line of sight and the disc's spin axis, i = 0 face-on, the quantity observers infer from the projected axis ratio (Hubble 1926; Holmberg 1958). position_angle is the roll of the image, the analogue of the sky position angle measured from north through east (de Vaucouleurs et al. 1991). Together they are the pair a tilted-ring fit assigns to each radius (Rogstad, Lockhart & Wright 1974; Begeman 1989).

azimuth turns the camera about the reference axis. For an axisymmetric disc the picture only rotates, so it is a movie parameter rather than a modelling one, and it reappears in Chapter 13.

`azimuth` is not `phi`

They cover the same directions when axis=:z, but the zero point differs by a quarter turn: inclination = theta, azimuth = phi + 90. phi is measured from +x, the usual spherical convention. azimuth starts 90 degrees later, so inclination=0 gives the same image orientation as direction=:z. Passing azimuth=phi rotates the picture by 90 degrees.

# Same window as Chapter 1, only `inclination` changes.
lad0  = projection(gas, :sd, :Msol_pc2; inclination=0,  axis=:angmom, win...)
lad30 = projection(gas, :sd, :Msol_pc2; inclination=30, axis=:angmom, win...)
lad60 = projection(gas, :sd, :Msol_pc2; inclination=60, axis=:angmom, win...)

# Is `direction=:faceon` the same as `inclination=0, axis=:angmom`? Separate the two halves of
# that question, the LINE OF SIGHT and the ROLL, because the answer differs for each.
println("max |ŵ_faceon − ŵ_inc0|     = ", maximum(abs, fo.los .- lad0.los))
println("angle(û_faceon, û_inc0)     = ",
        round(rad2deg(acos(clamp(sum(fo.up .* lad0.up), -1, 1))), digits=2), "°")
println("max |Σ_faceon − Σ_inc0|     = ", round(maximum(abs, lad0.maps[:sd] .- fo.maps[:sd]), digits=1))
# ... and the roll is recoverable exactly:
lad0_pa = projection(gas, :sd, :Msol_pc2; inclination=0, axis=:angmom, position_angle=-90, win...)
println("max |Σ_faceon − Σ_inc0,PA=-90| = ", maximum(abs, lad0_pa.maps[:sd] .- fo.maps[:sd]))

for (lbl, kw) in (("inclination + los", (inclination=35, los=[1,1,1])),

direction=:faceon and inclination=0, axis=:angmom give the same view: the same line of sight to the last bit, the same up vector, and a map difference of exactly zero.

A face-on view does not fix how the image is turned about the line of sight, so a rule has to choose it. Mera uses one rule for every way of pointing the camera: without up=, image up is world +z as the camera sees it, or +y when the line of sight is within 3 degrees of the z axis. inclination and azimuth are measured from the same reference, so inclination=0 is the face-on view, inclination=90 the edge-on view, and face_on(gas) passed to projection gives the same camera again.

The last printed line shows why one rule matters: turning the image by 90° changes the map by up to about 195 M⊙/pc². Two ways of asking for "face-on" that turned the image differently would disagree by that much.

3. Framing

Two ways to say what is in the picture, and they behave differently under rotation.

World ranges. xrange/yrange/zrange with center and range_unit select a box in the simulation, exactly as for the axis-aligned path and for subregion. The camera frame is then auto-fitted to the bounding box of that region after rotation, so:

  • the frame grows with tilt, and frames at different angles are not comparable
  • the window's own faces show up as straight edges across the image
  • with no zrange, the whole box depth of foreground and background sits in your disc map

fov. The camera is orthographic, so the only framing control is the half-width of the frame. fov selects a sphere about center, and a sphere projects to the same disc at every orientation. The frame is set by fov itself, centred on center, so it is the same at every angle and for every kind of data, whether the data fills the sphere or not.

apertureselectsframe
:circle (default)sphere of radius fovsquare array with empty corners, nothing cropped
:squaresphere of radius √2·fov, then croppedfull ±fov square, filled to the corners

Use :square for pictures and for frames you compare or animate, and :circle when you need a total, because the square crop drops what lies outside it.

`fov` always needs `fov_unit`

fov_unit defaults to :standard, which is a box fraction. fov=16 alone means 16 box lengths, silently clamped to the cap. Always write fov=16, fov_unit=:kpc.

What fov does, and which to use

fov is not a zoom. The camera is orthographic, so there is no distance to change. fov selects data, and for :square then crops the finished map:

  1. a subregion sphere about center, radius fov for :circle, √2·fov for :square
  2. projected onto a frame that fov fixes: symmetric about center, the same size at every angle, whether the data fills it or not
  3. for :square only, cropped to the central 2·fov / pixel pixels

Two side effects of step 1: fov replaces any xrange/yrange/zrange, and center is then read in fov_unit, so range_unit is discarded. Step 3 is the one that can cost mass: what lies in the sphere but outside the square is not on the map.

With no fov there is no sphere and no crop: every selected cell lands on the map, but the frame breathes with the viewing angle.

Without fov, a fitted frame is not a centred frame. The frame is then fitted to the extent of the selected data, not to its centre of mass. The gas fills the box, so the two agree. The stars do not: their centre of mass sits 8 pc from the box centre, but their extent runs −14.00 to +13.61 kpc across and −0.47 to +1.02 kpc vertically, set by a handful of outliers. 99.9 % of the stellar mass lies inside |z| < 0.21 kpc, so an edge-on star frame is set by about one star in a thousand and the disc sits visibly off centre in it. The dashed blue outline is what was asked for, drawn in the shape it was asked in: a square for xrange/yrange and for aperture=:square, a circle for aperture=:circle, which selects a disc and not a box. Those faces are worse than cosmetic. A sight line just inside the slab crosses its full depth; a sight line just outside clips only a corner. The column density therefore drops along a straight line, a hard edge that looks like a rendering artefact but is the selection box seen from an angle.

fov avoids all of this by framing the camera plane instead. The selection is a sphere, which projects to the same disc at every orientation, so the frame cannot breathe.

Mera prints a one-off note when it sees an off-axis view with a windowed xrange/yrange and no zrange, because the result is easy to mistake for a bug in the data.

Choosing fov

fov is a half-width: the frame spans ±fov, so fov=15, fov_unit=:kpc is a 30 kpc image.

A given fov buys an uneven depth. The selection is a sphere of radius R (fov for :circle, √2·fov for :square), so a ray at in-plane distance d integrates a chord, not a slab: depth(d) = 2·√(R² − d²). For fov=15, :square (R = 21.2 kpc):

The corners of a :square frame sit on the selection sphere and integrate nothing. That soft darkening in the corners of any fov map of a diffuse field is the selection boundary, not the gas. Chapter 4 is how you make the depth even.

Rule: make fov comfortably larger than the structure you are measuring, and never read a diffuse column, profile or scale height out to the frame boundary.

Picking one. Take the radius holding the mass fraction you care about and leave room. The gas disc here is about 23 kpc across with nine tenths of its mass inside 11.4 kpc, so fov=16 leaves it where the depth is nearly flat.

Changing it deliberately. A smaller fov is also a shallower column, so it removes foreground and background, and it buys resolution because the same pixels cover less sky. A larger one buys context and a deeper column, at the price of more unrelated material on every ray.

5. Whole cells or partial ones

A cut has to decide what to do with a cell it passes through. By default every off-axis cut keeps the cell whole if its centre is inside, and drops it whole otherwise. split=true weights it by the fraction of its volume that is really inside.

Reach for it when the edge is a real part of the measurement: a small aperture, a thin slab, or any time you stack slabs and expect them to re-sum.

split is grid only: it is not a keyword of the particle projection, so passing it is a MethodError. A point has no volume to split.

This is the same idea the region algebra already offers, and that one flows into off-axis maps too: subregion(gas, sphere(10; center=[:bc], range_unit=:kpc); split=true) attaches a :fraction column that getvar(:mass) and getvar(:volume) use.

Read the additivity line first. With whole cells, the pieces add up to more than the slab they came from, and cutting into more pieces does not make the error smaller. The reason is double counting: seen along [1,2,3], many cell centres lie exactly on a cut, and a cell whose centre is on the cut is kept by both neighbouring pieces. split=true gives such a cell a share on each side, so the pieces add up exactly.

The aperture line shows the same for a curved edge. With whole cells a small aperture gets too much mass, because the cells along its edge are a large part of a small sphere. With split=true the map holds the mass of the selected sphere, to round-off, at every radius.

The cost: split=true samples every cell that an edge passes through. Cells fully inside or outside need only a quick test, so the cost grows with the area of the cut, not with its volume.

6. Choosing the axis from the data

direction=:faceon, :edgeon and axis=:angmom all ask the same question of the data:

L = [sum(getvar(obj, :lx, center=center)),
     sum(getvar(obj, :ly, center=center)),
     sum(getvar(obj, :lz, center=center))]

Three things follow from this:

  • It is the whole loaded object, not the galaxy. Load a box and L is dominated by whatever carries the most angular momentum times lever arm, usually the outskirts. angmom_radius restricts the sum to a sphere about center.
  • It is measured about center. Wrong origin, confident and wrong axis.
  • It is per object. Gas and stars each have their own, so :faceon on one is a different camera from :faceon on the other.

For anything beyond one object's own axis, ask for the vector and reuse it:

angmom(gas; radius=[10,:kpc])from a sphere about center

angmom([gas, stars, dm]; ...)one axis from several components, momenta added
angmom(gas; vcenter=:auto)without the bulk motion of the object
face_on / edge_ona frame whose los/up/center splat into any call

Feed the result to any view with axis=L or los=L. It is also the cheap route: L costs a full pass over the data, and the presets recompute it on every call.

7. How a cell lands on the pixels

The camera is orthographic: every ray is parallel, the observer sits at infinity, nothing gets larger by being nearer. So there is no camera distance to set, and the only control over what is in frame is the width of the frame (Chapter 3).

A pixel is built from everything along the parallel ray through it, over the whole depth of the selected data: the sum for :mass, the sum over the pixel area for :sd, a weighted mean for everything else. In mathematical terms a pixel is a line integral through the data (the X-ray transform; Radon 1917; Natterer 1986), the same as volume rendering without absorption (Max 1995). This explains three things: a projection keeps the total mass, zrange matters as much as xrange, and a slice answers a different question (Chapter 12).

Why the footprint is a hexagon. Look at a cube from a general direction and you see the three faces meeting at the nearest corner; their outline is a circuit of six cube edges. It collapses to a rectangle only when the line of sight lies in a coordinate plane, which is exactly the axis-aligned, face-on and edge-on cases. Off-axis you are generically hexagonal.

Every cell is an axis-aligned cube, so for one camera every cell casts the same hexagon at a different scale: one footprint rule serves the whole AMR hierarchy.

`position_angle` is a roll

It turns (r̂, û) about ŵ, so the scene does not move. With aperture=:circle the selection is a disc and Σ is untouched; with :square the crop rotates inside the selection sphere and its corners sweep different material, so Σ moves a little.

Parallel rays, the image plane, and the camera basis (r̂, û, ŵ) planted at center. Right inset: inclination is measured from a reference axis, either the box z or the object's own angular-momentum axis L. They are not the same axis, and choosing the wrong one is the most common way to get a picture that looks right but is not. Tilted-ring fits of observed discs describe an orientation the same way, one inclination and one position angle per radius (Rogstad, Lockhart & Wright 1974).

The four kernels

The hexagon generally straddles several pixels. The four binning kernels are four answers to "how is it shared out". All four share it out completely, which is why the total is the same; they differ in where it lands.

The shape of the result does carry over, and it follows from how the kernels work. :exact integrates the footprint analytically; :overlap samples it with n³ sub-points, so a pixel is exact in the limit of many sub-points and noisy when few land in it.

  • The total is conserved either way, because both share out every cell completely. The one part in 10⁵ here is the crop of this fov frame, not a conservation floor; on an uncropped frame the floor is a few machine epsilon, and the test suite checks it.
  • The worst per-pixel disagreement is in the BRIGHT pixels: median 0.0017 dex faint, 0.0162 mid, 0.0205 bright. Bright pixels are where the structure is, so that is where the two kernels place mass differently.
  • :overlap is weakest on cells much coarser than the pixel, because it caps supersampling at nmax and :exact has no cap.

A faint pixel and a well-sampled pixel look the same on a colour scale. The count map says which is which: :ncell for cells, :npart for points, filled by the same deposit as the value.

Velocity along the line of sight, and across it

Two different frames, and confusing them is the most common error on this page.

framemeaning
:vz, :σzbox axesthe spread along the simulation z, whatever the camera is doing
:vlos, :σloscameraalong the line of sight, what a spectrum measures
:vcamx/:σcamx, :vcamy/:σcamycameraalong image x and image y

Both sets work off-axis. :σz on a face-on view is still the simulation z, which is almost never what a face-on view is asking about. The line-of-sight pair is the observable one.

The full box-frame set is :σx :σy :σz :σ :σr_cylinder :σϕ_cylinder :σr_sphere :σθ_sphere :σϕ_sphere, each built from its own v and v².

`:σ` is not the tensor trace

:σ is the spread of the speed, √(⟨|v|²⟩ − ⟨|v|⟩²). The trace of the dispersion tensor is σx² + σy² + σz² = ⟨|v|²⟩ − |⟨v⟩|². Different numbers, and :σ is the smaller one.

The camera triple and the box triple are one tensor in two frames, so σcamx² + σcamy² + σlos² = σx² + σy² + σz² pixel by pixel. The cell after next checks it.

What :σlos is, and is not

:vlos is signed so positive is receding, and it is defined for any camera. :σlos is √(⟨v_LOS²⟩ − ⟨v_LOS⟩²) over the mass in a pixel. With :sd and :vlos it completes the zeroth, first and second moments of the line-of-sight velocity distribution, the three maps an H I or CO cube is reduced to (Walter et al. 2008).

It is a width of a distribution inside one pixel, not a per-cell quantity: many cells along the ray land in the same pixel, each with its own v·ŵ. Edge-on that spread is dominated by ordered rotation along the sightline, not by turbulence. An observed dispersion carries the velocity gradient inside the resolution element and must be corrected before anyone calls it intrinsic (Davies et al. 2011).

Below, that shows up as the brightest σ_LOS off the disc plane: a sightline through the disc samples nearly co-rotating gas, one passing above it crosses infalling and outflowing material with a far wider spread.

Sign convention

:vlos follows the observational convention: positive means receding (redshifted), negative means approaching (blueshifted), exactly as a radial velocity is reported in a paper.

Note the relation to the camera. ŵ (m.los) points out of the image, toward the observer, so the map is -(v·ŵ). If you compute the projection yourself from m.los, remember that minus sign, or your rotation curve comes out inverted.

A sign flip inverts a rotation curve and changes nothing else in the figure, so check the shape too: on an edge-on map :vlos must be antisymmetric about the minor axis. If it is not, your center is off the object (Chapter 1).

Taking the rotation out

The edge-on σ_LOS above is mostly rotation, not turbulence: one line of sight crosses many radii that move at different speeds. This section takes the rotation out.

A dispersion already subtracts the mean inside each pixel, so a single bulk velocity changes nothing. What it cannot see is an ordered gradient along the ray. To remove that, subtract a velocity field before projecting.

rotation_frame measures the field from the data itself and restframe applies it, both described in How Quantities Are Computed. Two of its properties decide how the numbers below read. Cells are binned by cylindrical radius, 100 bins by default spread over the radial extent of whatever you hand it, and the model has no height dependence. The curve it returns is the curve of the material you measured it on, and it is then applied at every height. This is the simulation counterpart of correcting an observed dispersion for the velocity gradient across the beam (Begeman 1989; Davies et al. 2011).

# 300 pc, and the cost of this cell is the eight projections, four rotation frames and two
# subregions, not the grid: a projection is priced by the scan over the cells and hardly at all
# by the pixel count. The pixel-size sweep further up was measured on the UNCORRECTED field and
# does not carry over to the residual, which is a much smaller number made of different
# motions. If you quote a residual, measure its pixel-size behaviour again.
sig = (center=:bc, fov=15, fov_unit=:kpc, aperture=:square,
       pxsize=[0.3,:kpc], verbose=false, show_progress=false)     # note: no `direction` here
good(A) = filter(x -> isfinite(x) && x > 0, vec(A))

# THE CAMERA IS TAKEN ONCE, FROM THE UNCORRECTED OBJECT, AND REUSED.
# `direction=:edgeon` re-derives the view from the angular momentum of whatever it is handed, and
# `rotation_frame` removes the mass-weighted mean vϕ in every radial bin, which is most of L. The
# corrected object therefore has almost no net angular momentum left and its axis is set by what
# noise remains, so an "after" map asked for with :edgeon points somewhere arbitrary.
function rot_pair(g; nbins=100)
    f  = rotation_frame(g; center=:bc, nbins=nbins)   # the rotation curve measured from THIS gas
    gr = restframe(g; vcenter=f, center=:bc)
    A  = projection(g,  :σlos, :km_s; direction=:edgeon, sig...)   # camera fixed HERE
    B  = projection(gr, :σlos, :km_s; los=A.los, sig...)           # same camera, reused
    return median(good(A.maps[:σlos])), median(good(B.maps[:σlos]))
end

vcenter also takes a plain vector or :auto, so restframe(gas; vcenter=:auto) removes the bulk motion of the whole selection. That will not change a dispersion, which already subtracts the mean in each pixel; it matters for velocity maps. The thermal part

The dispersion above is the bulk spread of gas velocities. A real line is also broadened by thermal motion, and :σ_thermal gives that. It is √(P/ρ), it is isotropic, and it needs no μ. The formula and the reason it needs no μ are in How Quantities Are Computed.

What belongs here is how you combine it with a bulk width, because two rules are easy to break. Both numbers have to come from the same gas, and it is the variance that adds, because the line profile is a convolution:

\[\sigma_\mathrm{total}^2 = \sigma_\mathrm{bulk}^2 + \sigma_\mathrm{thermal}^2\]

        round(maximum(th), digits=2), " km/s   (whole box, so the top end is halo gas)")

One caveat if you are comparing against an observed line. :σ_thermal is the width of the mean gas particle, of mass μ m_H. A line is broadened by the mass of the emitting species, so for a species of mass m_X:

\[\sigma_{\mathrm{thermal},X} = \sqrt{P/\rho}\;\sqrt{\mu m_H / m_X}\]

Say which baseline you mean, because two are in circulation and they differ by more than a factor of two. Against atomic hydrogen, CO is 28 times heavier and its thermal width is √28, about 5.3, times narrower. Against the mean particle, which is what the formula above and √(P/ρ) are written in, the factor is √(μ m_H / m_X): about 6.8 for CO where μ = 0.6, and about 3.5 in molecular gas where μ = 2.3. Use getvar(gas, :mu) for the local μ. Draine (2011) sets out the thermal and turbulent line widths and the species-mass scaling in full.

9. Weighting and totals

mode decides whether a map is a weighted mean or a sum. On cell data (hydro, RT, gravity):

quantitymode=:standard (default)mode=:sum
:sd, :massthe total; mode is ignoredthe same

w is the weighting: mass for hydro, volume for RT, unless you choose another one.

`mode=:sum` on an ordinary quantity is not a total

projection(gas, :T, :K; mode=:sum) returns Σ T·m in each pixel, not Σ T, and the map's unit label still says K. The real unit is K times the unit of the weight, and with the default weighting=[:mass, missing] the mass is in code units. Use mode=:sum for :mass, :ekin, :etherm and :volume, or to integrate a density over volume: projection(gas, :rho, :g_cm3; mode=:sum, weighting=[:volume, :cm3]) gives Σ ρ·V, the mass in each pixel in grams. For anything else, keep the default mean.

:mass on particles

By default projection(part, :mass) is the mass-weighted mean particle mass, Σ(mᵢ·mᵢ)/Σmᵢ, because a particle has no volume to make it extensive.

That map has uses: with a particle mass spectrum it shows where the heavy particles sit; on a zoom it draws the boundary between resolution levels as a step in particle mass, the quickest way to see how far low-resolution contamination reaches; on any run a flat map means one particle mass and structure means more than one.

What it is not is a budget. For the mass in each pixel, ask for it:

projection(part, :mass, :Msol; mode=:sum, los=[1,2,3], center=[:bc])   # sums to the total

or use :sd times the pixel area.

The default sum drifts with pixel size, and passes through 1

Do not read that drift as an undercount converging on the right answer. Measured at los=[1,2,3] with :cic, sum(:mass)/M runs from 0.000156 at a 2.8 kpc pixel to 1.514 at 10 pc, straight through 1. A star split over four pixels makes all four report its full mass, so with one particle mass :cic could overshoot by 4; this run carries two, 800 and 1600 Msol, which lifts the bound to about 4·m_max/m_min, so 8. :ngp stays below 1, reaching 0.667. mode=:sum and sum(:sd·area)/M both stay at 1.

10. Masking

mask= takes one boolean per row of the object you pass, so any selection you can express as a vector can drive a map.

cold = getvar(gas, :T, :K) .< 1e4
projection(gas, :sd; los=[1,2,3], mask=cold, center=[:bc], fov=16, fov_unit=:kpc)

It composes with fov, depth, split and, on particles, parttypes. For value-space selection on any derived quantity, filterdata and getmask build the vector.

Without `fov`, a mask changes the frame

Without fov the frame is fitted to the selected cells, so a masked map and an unmasked one do not share a pixel grid and cannot be divided one by the other. Pass fov whenever you mean to compare them: then both maps get the same frame.

# One camera, three selections, one pinned frame so the three are comparable. `fov` is what
# makes them comparable: without it each map would fit its own extent.
# `aperture=:circle`: a sphere is a selection and nothing is cropped after it, so every
# selected cell reaches the map and the two parts can be checked against the whole. A total is
# never read off a `:square` map, which drops what lies outside the square.
mkw = (los=[1.,2,3], center=[:bc], fov=16, fov_unit=:kpc, aperture=:circle,
       pxsize=[0.2,:kpc], verbose=false, show_progress=false)
cold = getvar(gas, :T, :K) .< 1e4
hot  = .!cold

A slab instead of a slice, for particles

A cutting plane through point particles catches nothing: a particle has no extent, so a zero-thickness plane is empty by construction. That is why slice(part, …) is a MethodError rather than an oversight.

The useful analogue is a projection of finite depth. thickness sets the depth of the slab along the line of sight and offset moves it, the same way offset moves the plane for cell data. A non-positive thickness is refused rather than returning an empty map.

Same keywords, same camera, three kinds of data. The stars form a thinner, smoother disc than the gas, which is why it helps to map both in one orientation. The potential is smoother than either: it depends on all the mass, not on the clumps that dominate the gas map, and its contours are rounder than the disc.

Gravity comes through the two-object form, projection(hydro, gravity, var): the hydro object supplies the weights, because gravity carries none of its own (How Quantities Are Computed). Both must describe the same cells, so load them from the same info at the same lmax. fov cuts both together, so the three panels above are framed identically and can be compared pixel for pixel.

What does differ between the two data types is the deposit itself: points have no footprint, so particle projections use :cic and the footprint kernels fall back to it.

That difference is visible if you push the pixels: a grid map degrades smoothly, while a particle map becomes grainy, because each pixel is counting a finite number of objects and inherits a √N uncertainty. The cure is the same as in any counting experiment, coarsen the pixels until each one holds enough particles to mean something.

What these star particles are, and what is missing

Every particle in this snapshot was made by the simulation itself. All 627,896 are stars (family = 2), there are no dark matter particles, and their birth times run from 4.2 Myr to 580.0 Myr, which is the full age of the run. Together they hold 5.0·10⁸ solar masses, about one percent of the stellar mass of the model galaxy, 1.03 percent measured against the old stellar disc on its own. The old disc, the bulge and the dark halo are not particles at all. They are an analytic mass distribution that the run adds to the Poisson source (gravity_type = -3), worth roughly 4.9·10¹⁰ solar masses for the old stellar disc, 1.5·10¹⁰ for the bulge and 1.4·10¹¹ for the halo. So this map shows recent star formation, not the stars of the galaxy: there is no bulge in it because the bulge was never made of particles.

Inside the central 500 pc the analytic bulge outweighs the star particles by about 50 to 1, 8.9·10⁸ solar masses against 1.75·10⁷, so the brightest part of a real galaxy's stellar image is the part this panel does not contain at all.

The potential panel is the other half of that story. The analytic components enter the Poisson source, so the stored potential does include the bulge, the disc and the halo, and :epot maps the mass the star panel cannot show. The two panels disagree about what this galaxy is made of, and each is right about its own tracer.

Stars: what a point mass conserves

The camera does not change. What changes is the thing being deposited.

A cell has a volume: it covers pixels, it has a chord along the ray, and Chapter 7 is about what happens when a pixel becomes smaller than that footprint. A star particle is a point mass at one position, so there is nothing to integrate over, nothing for a cutting plane to catch, and no smallest scale below which the map stops changing.

  • binning keeps two of its four values, and only off-axis. Along a box axis the particle path is a plain histogram, which is :ngp, and binning is not read at all. Write los=[0,0,1] if you want CIC along z.
  • weighting is a plain Symbol, and on star particles :mass is the only value that means anything.
  • :sd is the map that conserves mass, or :mass with mode=:sum (Chapter 9).
  • The peak surface density has no converged value, because a point mass is a delta function.

The two moments, and what a stellar width is made of

:vlos and :σlos mean for stars exactly what Chapter 8 says they mean for gas, sign convention included: positive is receding. What differs is what the width is made of. Gas carries a thermal width that has to be added in quadrature. A collisionless star does not, so the stellar σ_LOS is the second moment of the line-of-sight velocity distribution and nothing else, which is the quantity an integral field spectrograph reports.

Because every particle deposits its whole mass, the per-pixel moments obey the law of total variance exactly. The global mass-weighted variance of v_LOS is the mass-weighted mean of the per-pixel variance plus the mass-weighted variance of the per-pixel mean. Which of the two terms holds the variance moves with the pixel size, and their sum does not: coarse pixels swallow whole radii of the disc and keep the variance inside pixels, fine pixels resolve the rotation and hand it to the between-pixel term. That is the Chapter 8 statement seen from the budget side. One condition, if you check it on your own data: the weights and the two moments have to come from the same call, because they have to be the same deposit.

One caveat is specific to points. The per-pixel σ_LOS is the population variance of the stars in that pixel, not the sample variance. With N stars it is low by a factor (N-1)/N against the width of the distribution those stars were drawn from: half the variance for two stars, and exactly zero for one. Splitting a star over four pixels with :cic does not help, because all four copies carry the same velocity. The identity is untouched, since it is bookkeeping over the deposited weights, but a stellar dispersion map is biased low wherever the pixels are sparse.

The peak surface density has no converged value

A star is a delta function. The pixel holding it reports m★/Δ², so once the densest pixel is down to a single star, halving the pixel quadruples the peak, and it goes on doing that without limit. There is no pixel size at which a stellar peak surface density converges. Gas is genuinely different: a cell has a finite volume and a finite density, so below the finest cell the gas peak stops moving.

The same counting sets the noise, and that part you do on your own data. Spread these stars over a disc of radius 11.4 kpc and the mean is about 1540 per square kpc, so a pixel of side Δ holds about 1540·Δ² of them and carries at least a √N fluctuation:

What the angle does, and what it does not

Turning the camera cannot change the stellar mass. What it does change is the shape of the image and the kinematics, and both change in a way you can predict before you run it:

  • the apparent axis ratio goes as cos i for a razor-thin disc. A real disc has thickness, so q² = cos²i + q₀²·sin²i and q stops above zero at i = 90. That is the relation observers invert to get an inclination out of an image (Hubble 1926; Holmberg 1958), and the residual at edge-on is the intrinsic thickness q₀.
  • the line-of-sight velocity amplitude goes as sin i, because only the component of the rotation along the ray is visible.

The first column below is not the conservation test, it is the fraction of the stellar mass the frame selected. fov with aperture=:circle selects a sphere, and a sphere looks the same from every angle, so that column should not move as the camera turns. What it falls short of 1 by is the stellar mass outside 16 kpc. Conservation itself needs a frame that crops nothing, so it is checked without fov.

# flux-weighted second moments of the Σ image, above an isophotal cut so the faint rim does not
# set the shape
function axisratio(m; cut=0.05)
    A  = Float64.(m.maps[:sd]); e = getextent(m, :kpc)
    xs = collect(range(e[1], e[2], length=size(A,1)))
    ys = collect(range(e[3], e[4], length=size(A,2)))'
    A  = A .* (A .> cut * maximum(A))
    W  = sum(A); xb = sum(A .* xs) / W; yb = sum(A .* ys) / W
    Sxx = sum(A .* (xs .- xb) .^ 2) / W
    Syy = sum(A .* (ys .- yb) .^ 2) / W
    Sxy = sum(A .* (xs .- xb) .* (ys .- yb)) / W
    t = (Sxx + Syy) / 2; d = sqrt(((Sxx - Syy) / 2)^2 + Sxy^2)
    sqrt((t - d) / (t + d))
end

Five things to carry away.

:sd is the conserved map. If you need a stellar mass out of a map, it is sum(m.maps[:sd]) * (m.pixsize * m.scale.pc)^2, with m.pixsize and no aperture=:square crop. :mass is the mass-weighted mean particle mass, worth having for its own sake and not a total. The test suite checks that recipe over viewing angle, pixel size and both kernels.

fov gives points the same frame as cells, so a particle panel lines up with a gas panel without help. Use :circle when you need a total, because :square crops what lies outside the square.

:rho on particles divides the pixel mass by the whole box length, not by the depth you selected, so a slab's :rho is not a slab mean density. Use :sd.

Empty pixels are 0.0 almost everywhere, and NaN in one place. Every off-axis map writes 0.0, and so does an axis-aligned hydro map. The exception is the axis-aligned particle path, which divides two deposited grids, so an empty pixel of a weighted-mean map comes back NaN there. A filter(isfinite, ...) therefore keeps every empty off-axis pixel and quietly drags a median toward zero. Mask by :sd, as the figure above does.

Stellar L is not gas L. direction=:faceon on part takes the stars' own angular momentum and on gas the gas's, so a stars-versus-gas comparison in one frame needs one explicit axis=[lx, ly, lz] passed to both. The recipe at the end of the page makes the same argument for a time series.

12. Slices: a sample, not an integral

slice takes the same view keywords as projection and returns the cells the plane passes through. (offaxis_slice is a documented alias; prefer slice.) Given slice_axis/slice_pos instead of a view it cuts along a box axis, which the covering grid page covers.

It is a nearest-cell sample, not an integral:

  • Nothing is conserved, because no ray is integrated. Never sum a slice.
  • Empty (NaN) pixels are geometry, not failure: where the plane threads between refinement levels there is no cell.
  • The tilted blocks are the true shape of the cut. A plane crossing an axis-aligned cube at an angle gives a quadrilateral cross-section.

What a slice can report per pixel, since exactly one cell owns each:

fieldis
sl.mapthe value, NaN where nothing was painted
sl.coveragewhich pixels were painted
sl.cellsizethe size of the cell that won each pixel
sl.depthhow far along the view that cell sat

There is no cell count, because it would read 1 everywhere. cellsize against pixsize is the useful one: where the cell is larger than the pixel, the extra pixels carry no extra information.

The API is the opposite of Chapter 3

On slice, xrange/yrange are the camera-plane window. There is no fov and no binning, it takes one variable, and it works on cell data only. Depth is set by offset, not zrange. slice(part, …) is a MethodError by design; the particle equivalent is a projection of finite thickness (Chapter 11). Its .extent and .center are code units, unlike a map's.

The same exercise on points: a slab, not a plane

A plane cannot sample a star, so the slice figures above have no star version. The counterpart for stars is a slab: a projection with a small depth. It answers the same question as a slice, for a thickness you choose.

A slice reports one cell per pixel; a slab reports everything inside a given depth. For point data only the slab exists.

The slab moves in depth the way offset moved the plane. The view is face-on, so the line of sight is the z axis, and moving the slab in z moves it towards or away from the observer.

13. Turning the camera: orbit movies

rotation_sequence renders one variable over a list of angles and returns a Vector of maps. sweep=:azimuth (default), :inclination or :position_angle picks which angle varies. It calls projection once per angle, so the same sweep runs on particles.

It uses the framing rule of Chapter 3, swept: a rotation-invariant sphere, aperture=:circle or :square. That is why it exists, because a cubic window's rotated bounding box changes size frame by frame and the movie breathes.

One difference from `projection`

Omit fov here and it auto-fits to the 99 % enclosed-mass radius, so the frame follows the object rather than the sparse outermost cells. projection has no auto-fit: omit fov there and you are back on world ranges. Pass fov explicitly whenever it matters.

parallel_frames=true runs frames concurrently with single-threaded projections, typically 1.5 to 2 times faster when there are at least as many frames as threads, at proportionally more transient memory. Keep the total at or below 8 threads on a laptop.

frames = rotation_sequence(gas, :sd, :Msol_pc2; sweep=:azimuth, angles=0:90:270,
                           inclination=55, axis=:angmom, center=[:bc],
                           fov=16, fov_unit=:kpc, aperture=:square,
                           pxsize=[0.1,:kpc], parallel_frames=false)

Four azimuths, and the frame size and extent are the same to three decimals, in the pictures and in the numbers. That is what makes the sequence usable as a movie: the frame does not change size, so the eye sees a turn, not a zoom.

Turning the frames into a movie is one Makie.record call. Makie brings its own ffmpeg (through FFMPEG_jll), so nothing has to be installed, and the movie below is made by the notebook itself.

Frames or pixels? A frame costs mostly the time to read the cells, and a finer pixel adds little while the pixel is larger than the cells. So spend the time on frames, which make the turn smooth; the pixel size is nearly free. Below the cell size this reverses (Chapter 1). Orientation. position_angle= rolls the image about ŵ; up= pins image y outright. Without up= the camera uses world +z as its hint, falling back to +y when the line of sight is within 3 degrees of the z axis. That fallback is a discontinuity: a sweep that passes through the pole will jump there. Pin up= for any hand-written sweep, or use rotation_sequence, which sets a hint for you.

Grid diagnostics. gridoverlay(gas; level=:max, <same view kwargs>) draws the AMR structure in the camera frame. Off-axis it draws cell-size squares at rotated cell centres, not the true hexagonal footprints, so it tells you where and how big cells are, not what shape their shadows have.

Limitations, in one place

What the chapters above establish, one line each. One thing that is not a limitation, because the test suite pins it: the map total is the object's total to a few machine epsilon at any angle, pixel size, kernel and nmax.

Orthographic onlyparallel rays, observer at infinity. No perspective, no view from inside the box
World ranges are not depthxrange/yrange/zrange are world space and the frame auto-fits the rotated footprint. For a cut along the view, use depth (Chapter 4)
zrange can be a no-opan axis whose requested range already covers the loaded data is not clipped at all
Cuts are cell-centre by defaulta straddling cell is kept or dropped whole, so a world-range selection is accurate to about one cell per face (0.75 kpc at level 6 here). split=true weights depth and fov by volume instead (Chapter 5); world ranges stay cell-centre
Border fold-backa deposit that crosses the map edge is added to the edge pixel. It rarely happens off-axis, because the frame is padded so border cells fit. A square crop or the face of a world-range box does reach the edge, so the outermost row is still not a clean measurement
fov trapsfov_unit defaults to a box fraction; fov replaces xrange/yrange/zrange; center is then read in fov_unit
A mask changes the frame without fovthe extent fits the selected cells, so masked and unmasked maps do not share a pixel grid. With fov they do (Chapter 10)
Frames match, but not bit-exactlyaperture=:square gives identical pixel dimensions and physical scale at every angle; co-registration is good to the auto-fit rounding
nmax=64zoom far enough into a coarse region and :overlap deposits a top-hat rather than a 64³ lattice. It costs placement, not mass: measured on this snapshot, a 43.7-fold change in per-pixel agreement with :exact while the total never leaves ±2 machine epsilon. Raise nmax, or use :exact
Off-axis ≠ axis-aligned pixel gridsdifferencing los=[0,0,1] against direction=:z shows a sub-pixel origin offset. A grid convention, not an error
Axis-aligned only:r_cylinder, :r_sphere, :ϕ. They describe the pixel's own geometry, and an off-axis pixel is a slanted column
:mass is a mean on particlesunless you pass mode=:sum. On cell data it is the summed column (Chapter 9)
Result-object quirksmaps_lmax is empty; maps_weight is AMR-only; .center is a box fraction on a map but code units on a slice; a mass-weighted call returns a bonus :sd map; lmax off-axis only sets the default resolution and never coarsens the data

Recipe: one fixed orientation across a time series

The most common way a multi-snapshot off-axis analysis goes wrong: direction=:faceon is called per snapshot, the disc's L drifts (warp, bar, merger, an infalling satellite), and the resulting movie tumbles or the measured inclination wanders.

The fix is to compute the orientation once, on the region you actually mean, and then freeze it:

# NOT EXECUTED: this page uses a single output (output_00390).
# Shown for the mechanics; substitute your own output list.

# 1. Orientation from the INNER DISC of one reference snapshot, not the whole box.
#    L over the full box is dominated by slow, high-lever-arm CGM gas, which is
#    why a whole-box "face-on" can be 10 to 30 degrees off for a warped or fountain-rich disc.
ref  = loaddata(390, path, :hydro; verbose=false)
disc = subregion(ref, :cylinder, radius=8., height=2., range_unit=:kpc,
                 center=[:bc], verbose=false)
Lfix = [sum(getvar(disc, :lx, center=[:bc])),
        sum(getvar(disc, :ly, center=[:bc])),
        sum(getvar(disc, :lz, center=[:bc]))]
Lfix ./= sqrt(sum(abs2, Lfix))

# 2. Project every snapshot with that ONE frozen line of sight and a fixed FOV.
#    `up=` is pinned too. The default hint is world +z, which is stable, but it
#    falls back to +y if a line of sight comes within 3 degrees of z, and that is a jump.
for out in outputs
    g = loaddata(out, path, :hydro; verbose=false)
    m = projection(g, :sd, :Msol_pc2; los=Lfix, up=[0,0,1], center=[:bc],
                   fov=16, fov_unit=:kpc, aperture=:square, pxsize=[0.3,:kpc],
                   verbose=false, show_progress=false)
    savemap(m, "faceon_$(out).jld2", verbose=false)
end

A drifting orientation is not a cosmetic problem: viewing angle biases the quantities measured from an image, so a time series taken at a wandering angle is not a time series of the galaxy (Bottrell et al. 2017). Gas L and stellar L are not the same vector either (bars, warps, counter-rotating components), so decide which tracer defines your frame and stick to it. And note that this is also how you get a comparable frame: the same los, the same fov, the same pxsize, so every snapshot is the same camera.
