MERA Files API Reference

Docstrings for Mera's own save format, an LZ4-compressed JLD2 file that round-trips a loaded object far faster than re-reading the simulation. The narrative guides are Mera-Files and Converter.

The file stores the Julia object, so it is a Julia-side format: reload it with loaddata, not with h5py. To hand results to another language use exportdata (below), or export_vtk for ParaView and VisIt.

Save & load

Mera.savedata — Function
savedata(data; fmode, path="./", kwargs...)
savedata(data, fmode::Symbol; path="./", kwargs...)
savedata(data, path::String; fmode, kwargs...)
savedata(data, path::String, fmode::Symbol; kwargs...)

Save a Mera data object to a compressed JLD2 file, a "Mera file", which reloads much faster than the original RAMSES output.

One file per output holds any number of data types (hydro, particles, gravity, clumps, RT, sinks). The file is named after the output number, e.g. output_00300.jld2, and keeps the table together with the simulation information and the options it was loaded with.

Arguments

  • data: the object to save, from gethydro, getparticles, getgravity, getclumps, getrt or getsinks.
  • fmode::Symbol: what to do with the file. Nothing is written unless it is given, so a file is never overwritten by accident.
    • :write: create the file, or replace an existing one.
    • :append: add a further data type to an existing file. A data type that is already in the file is not replaced; that raises an error.
  • path::String = "./": the folder to write to.

Keywords

  • fname = "output_": the start of the file name; the five-digit output number follows.
  • compress: LZ4 compression is on by default; compress=false switches it off. Older compressor objects are accepted, and Zlib or Bzip2 fall back to LZ4 with a warning.
  • comments: a text stored with the data, e.g. a description of the simulation.
  • dataformat::Symbol = :JLD2: the only format.
  • merafile_version::Float64 = 1.0: the file layout version; there is only one.
  • sidecar::Bool = true: also write output_XXXXX.jld2.meta.json, a readable record of the data types in the file, their provenance and the environment; an append adds to it. The global switch sidecar overrides this keyword.
  • anonymize::Bool = false: in the sidecar, keep only the last two parts of the simulation path.
  • note::String = "": a free text stored in the sidecar.
  • include_script::Bool = false: also store the full text of the running script (or the code cells of the notebook) in the sidecar. Its name and SHA-256 are always recorded, when Julia knows the script.
  • verbose::Bool = true: print what is written.

Examples

julia> savedata(gas, :write; path="mera_files/");     # new file output_00300.jld2

julia> savedata(part, :append; path="mera_files/");   # add the particles to it

julia> viewdata(300; path="mera_files/")              # what the file holds

See also loaddata, viewdata, infodata, convertdata.

Returns nothing.

Mera.loaddata — Function
loaddata(output::Int, datatype::Symbol; path="./", kwargs...)
loaddata(output::Int, path::String, datatype::Symbol; kwargs...)
loaddata(output::Int; datatype, path="./", kwargs...)
loaddata(output::Int, path::String; datatype, kwargs...)

Load one data type from a Mera file written by savedata.

The stored table is read in full; a region given by the ranges is then cut out. Files written by any earlier Mera version can be read.

Arguments

  • output::Int: the output number in the file name, e.g. 300 for output_00300.jld2.
  • datatype::Symbol: the data type to load: :hydro, :particles, :gravity, :clumps, :rt or :sinks. It is required, as a positional argument or as a keyword.
  • path::String = "./": the folder of the file.

Keywords

Selection:

  • xrange, yrange, zrange: [min, max] of the region to keep, in range_unit and relative to center. missing (the default) means the full extent.
  • center = [0, 0, 0]: the origin of the ranges, in range_unit. [:bc] is the box centre.
  • range_unit::Symbol = :standard: the unit of the ranges and the centre. :standard means fractions of the box (0 to 1); any length unit in info.scale works, e.g. :kpc.

File:

  • fname = "output_": the start of the file name, as given to savedata.
  • regenerate_scales::Bool = true: recompute the physical constants and unit scales with the current Mera version. false keeps exactly what was stored.

Output:

  • verbose::Bool = true: print what is read.
  • myargs::ArgumentsType: set the ranges, center, range_unit and verbose in one object. A keyword given directly takes precedence.

Returns

The stored object, e.g. a HydroDataType for :hydro, the same as the function that first read it returned.

Examples

julia> gas = loaddata(300, :hydro; path="mera_files/");

julia> part = loaddata(300, "mera_files/", :particles; xrange=[-10, 10], yrange=[-10, 10],
                       zrange=[-2, 2], center=[:bc], range_unit=:kpc);

See also savedata, viewdata, infodata.

Export for other tools

exportdata writes a projection, a profile, phase or pdf, a timeseries table, a movie, or plain arrays to .h5, .jld2, .csv, .npy, .npz, .json or .fits (the last after using FITSIO). The file holds plain arrays that Python, IDL or a spreadsheet read directly. The tutorial Exporting Data shows each format and how to read it in Python.

Mera.exportdata — Function
exportdata(result, file; format=:auto, vars=nothing, source=nothing,
           length_unit=:standard, sidecar=true, anonymize=false, note="",
           include_script=false, verbose=true) -> String

Write a Mera result to a file that other tools read, and a sidecar <file>.meta.json that records what it holds and where it came from.

Use it to publish the data behind a figure, or to continue in Python, IDL or a spreadsheet. The file holds plain arrays; the sidecar holds the provenance, the units and the environment that ran (the Reproducibility page explains it). To keep a result for Mera itself, use savemap or savedata instead: they round-trip the full object.

Arguments

  • result: what to write.
    • a projection from projection: every map, plus the pixel centres x and y;
    • a profile, phase or pdf result;
    • a timeseries table;
    • a movie from getmovie: the frames as a cube, plus outputs and times;
    • an array, a number, or a NamedTuple of arrays, e.g. getvar columns. Pass source so the sidecar knows which snapshot they came from.
  • file::String: the file to write. Its extension selects the format.
extensionformatholds
.jld2JLD2 (HDF5 container)all arrays, readable with h5py
.h5, .hdf5HDF5all arrays, each with a unit attribute
.csvCSVa table: one row per pixel of a map or phase diagram, or per bin of a profile
.npyNumPyexactly one array
.npzNumPy archiveall arrays
.jsonJSONall arrays, for small results (at most 10⁶ values)
.fitsFITSone image per array, maps with a linear WCS; needs using FITSIO

Keywords

  • format::Symbol = :auto: the format, :jld2, :hdf5, :csv, :npy, :npz, :json or :fits; :auto takes it from the extension.
  • vars = nothing: write only these arrays, e.g. vars=:sd or vars=[:mean, :median]. The coordinates (pixel centres, bin edges) are always kept.
  • source = nothing: the data object or InfoType the result was computed from. Needed for arrays, numbers and timeseries tables, which do not carry it; a map, profile, phase or pdf carries it already.
  • length_unit::Symbol = :standard: the unit of a map's pixel centres, extent and pixel size, e.g. :kpc. :standard keeps code units. Maps only.
  • sidecar::Bool = true: write <file>.meta.json. The global switch sidecar overrides it.
  • anonymize::Bool = false: in the sidecar, keep only the last two parts of the simulation path. The host name is never recorded.
  • note::String = "": a free text stored in the sidecar, e.g. which figure this is.
  • include_script::Bool = false: also store the full text of the running script (or the code cells of the notebook) in the sidecar. Its name and SHA-256 are always recorded, when Julia knows the script.
  • verbose::Bool = true: print what was written.

Python and other C-order readers see the axes of an HDF5 or JLD2 array reversed (a Julia nx × ny map has shape (ny, nx) in h5py). NumPy files are written in Fortran order, so there a[i, j] is A[i+1, j+1]. The sidecar states the layout of each file.

Returns

The path of the data file, as a String.

Examples

p = projection(gas, [:sd, :T], [:Msol_pc2, :K])
exportdata(p, "fig3.h5"; length_unit=:kpc)          # + fig3.h5.meta.json
exportdata(p, "fig3_sd.npy"; vars=:sd)              # one map for numpy
exportdata(p, "fig3.csv"; length_unit=:kpc)         # x, y, sd, T per pixel

prof = profile(gas, :r_cylinder, :rho; xunit=:kpc, unit=:nH)
exportdata(prof, "fig4.csv"; note="Figure 4, radial density")

exportdata((rho=getvar(gas, :rho, :nH), T=getvar(gas, :T, :K)), "cells.npz"; source=gas)

using FITSIO
exportdata(p, "fig3.fits"; length_unit=:kpc)

See also savemap, savedata, provenance, export_vtk.

Next to every saved or exported file Mera writes a sidecar, <file>.meta.json: what the file holds and in which units, the SHA-256 of the file, the provenance of the snapshot, the SHA-256 of the run's namelist.txt, makefile.txt, patches.txt and compilation.txt, the Julia, Mera, CPU and thread count that ran, and the analysis around it: the SHA-256 of your Project.toml and Manifest.toml and of the script that ran. It is JSON, so any language reads it. The host name is never recorded. sidecar=false on a call, or sidecar(false) for the whole session, turns it off; so does the environment variable MERA_SIDECAR=0, without changing a script. The first sidecar of a session prints one line saying what the new file is. Mera also says once when the sidecar cannot pin down what ran: in the shared environment the recorded Manifest.toml changes with every package you add, and in a Mera checkout with uncommitted changes the recorded commit is not the code that ran.

A figure is saved by the plotting package, so Mera does not see it: call writesidecar right after the save to give it the same record, taken from the results it shows. save_clumps writes a sidecar too; pass source= to record the snapshot.

readsidecar prints one sidecar and checks that its data file still matches the recorded SHA-256; sidecaroverview lists every sidecar in a folder. The tutorial Sharing results shows them on a real simulation.

Before publishing, bundle joins the sidecars of an analysis folder into one RO-Crate record, ro-crate-metadata.json, with a software.bib to cite. meraproject starts a new analysis folder with its own environment, so the sidecars record exactly the packages that ran.

Mera.writesidecar — Function
writesidecar(file, source=nothing; note="", anonymize=false, include_script=false, verbose=true)

Write the sidecar <file>.meta.json for a file that Mera did not write itself, typically a figure saved with Makie, PyPlot or Plots. The sidecar is the same as for exportdata: the SHA-256 of the file, the provenance of the snapshot, the input files of the run, the analysis environment and script, and the Julia and Mera that ran.

Call it right after the save:

save("fig3.png", fig)               # Makie
writesidecar("fig3.png", p)         # p: the projection shown in the figure

Arguments

  • file::String: an existing file.
  • source: the Mera result the file shows (a projection, profile, data object, movie or InfoType), or a vector of them for a figure with several panels. With nothing the sidecar still records the file, the analysis and the environment, but no snapshot.

Keywords

  • note::String = "": a free text stored in the sidecar, e.g. "Figure 3 of the paper".
  • anonymize::Bool = false: keep only the last two parts of the simulation path.
  • include_script::Bool = false: also store the full text of the running script (or the code cells of the notebook). Its name and SHA-256 are always recorded, when Julia knows the script.
  • verbose::Bool = true: print the sidecar's path.

Returns

The sidecar's path as a String, or nothing when sidecars are switched off with sidecar(false) or the sidecar could not be written (a warning says why). An existing sidecar of the file is replaced.

Examples

writesidecar("fig3.png", p; note="Figure 3")
writesidecar("evolution.pdf", [p10, p20, p30])   # one panel per snapshot
readsidecar("fig3.png")                          # read it back

See also readsidecar, sidecaroverview, exportdata.

Mera.readsidecar — Function
readsidecar(file; verify=true) -> SidecarRecord

Read the sidecar of a file written by savedata, savemap, savemovie, save_clumps, exportdata or writesidecar, and print a short summary in the REPL.

Arguments

  • file::String: the data file (fig3.h5) or its sidecar (fig3.h5.meta.json).

Keywords

  • verify::Bool = true: compare the data file with the SHA-256 in the sidecar, so status says whether it changed since it was written. Reading a large Mera file takes a few seconds per GB; verify=false skips it.

A SidecarRecord; r.data holds the whole record, e.g. r.data["source"]["output"].

Examples

r.data["environment"]["julia_version"]

See also sidecaroverview, writesidecar, exportdata, sidecar.

Mera.sidecaroverview — Function
sidecaroverview(dir="."; recursive=false, verify=false, verbose=true) -> Vector{SidecarRecord}

List every sidecar (*.meta.json) in a folder as a table: the file, what it holds, the snapshot it came from, when it was written, and whether the data file is still there.

Arguments

  • dir::String = ".": the folder to look in.

Keywords

  • recursive::Bool = false: also look in subfolders.
  • verify::Bool = false: compare every data file with its recorded SHA-256 (slow for large files); the status column then says unchanged or changed.
  • verbose::Bool = true: print the table.

Returns

A Vector of SidecarRecord, sorted by file name.

Examples

sidecaroverview("results/")                  # one line per saved or exported file
recs = sidecaroverview("results/"; verify=true, verbose=false)
filter(r -> r.status === :changed, recs)     # files edited after they were written

See also readsidecar, exportdata.

Mera.bundle — Function
bundle(dir="."; title=nothing, description=nothing, creators=nothing, license=nothing,
       keywords=String[], simulation=nothing, recursive=true, verify=true, verbose=true) -> String

Describe a finished analysis folder in one record, ready to publish, for example on Zenodo. bundle reads the sidecars in the folder and writes three files into it:

  • ro-crate-metadata.json: an RO-Crate that lists every file with its size, type and SHA-256, and for each file written by Mera what made it: the Mera version, the script and the snapshot, from its sidecar;
  • software.bib: the BibTeX from citation;
  • simulation.json: the simulationrecord, when simulation is given.

Nothing is copied, so the folder needs no extra disk space. Running it again replaces the three files.

Arguments

  • dir::String = ".": the analysis folder.

Keywords

  • title, description, creators, license, keywords: who made the analysis and under which license, as for datacite: creators as "Family, Given" or (name=…, orcid=…, affiliation=…), license as an SPDX identifier such as "CC-BY-4.0". Missing ones are read from an analysis.toml in the folder (the same fields as simulation.toml, see meraproject); the title falls back to the folder name.
  • simulation = nothing: the simulation the analysis used: a folder, an InfoType or a SimulationRecord. Its record is written to simulation.json.
  • recursive::Bool = true: include subfolders. Hidden files and folders are left out.
  • verify::Bool = true: check each file against the SHA-256 in its sidecar, and warn about files that changed after they were written.
  • verbose::Bool = true: print a summary.

Returns

The path of ro-crate-metadata.json.

Examples

bundle("galaxy_paper"; simulation="/data/mw_L10",
       creators=["Behrendt, Manuel"], license="CC-BY-4.0")

See also meraproject, sidecaroverview, citation, datacite.

Mera.meraproject — Function
meraproject(dir; title=nothing, verbose=true) -> String

Start a new analysis folder with its own Julia environment, so every sidecar records exactly the packages that ran. It writes:

  • Project.toml, with Mera at the version that runs now;
  • analysis.jl, a first script;
  • analysis.toml, the title, authors and license of the analysis, for bundle;
  • README.md, the few steps from the first run to publishing.

Nothing is installed and no network is needed: the first julia --project=. in the folder, followed by ] instantiate, installs Mera there.

Arguments

  • dir::String: the new folder. It may exist, but must not hold a Project.toml yet.

Keywords

  • title::String = nothing: the title of the analysis, stored in analysis.toml; defaults to the folder name.
  • verbose::Bool = true: print the next steps.

Returns

The folder's path.

Examples

meraproject("galaxy_paper")
# then, in a terminal:
#   cd galaxy_paper
#   julia --project=.
#   ] instantiate

See also bundle, writesidecar.

Mera.SidecarRecord — Type
SidecarRecord

What readsidecar and sidecaroverview return for one sidecar: file (the data file), sidecar (the .meta.json), data (the parsed JSON, index it like a dictionary, e.g. r.data["source"]["output"]) and status: :unchanged or :changed when the file's SHA-256 was checked, :missing when the data file is gone, :unchecked otherwise.

Mera.SimulationRecord — Type
SimulationRecord

What simulationrecord returns: data, the record as an ordered dictionary (index it directly, e.g. rec["resolution"]["levelmax"]), and path, the simulation folder. It prints a short summary in the REPL. Write it as JSON with writesimulationrecord, or turn it into DataCite metadata with datacite.

Mera.convertdata — Function

Converts full simulation data into a compressed/uncompressed JLD2 format:

This function provides a comprehensive data conversion workflow for RAMSES simulation data, converting multiple data types into compressed JLD2 format with full benchmarking and threading control capabilities.

Features:

  • Multi-datatype support: Handles :hydro, :particles, :gravity, :clumps, :rt, :sinks data types
  • Threading control: Configurable threading for performance optimization (excluding clumps)
  • Compression options: Multiple compression algorithms with automatic selection
  • Spatial filtering: Select specific data ranges with flexible unit support
  • Benchmarking: Comprehensive timing and performance statistics storage
  • Progress tracking: Optional progress bars and verbose output modes
  • Memory management: Automatic memory cleanup and usage tracking

Data Processing Workflow:

  1. Configuration: Parse arguments and setup threading/compression parameters
  2. Data Loading: Sequential loading of requested datatypes with optional threading
  3. Data Writing: Compressed storage to JLD2 format with timing measurements
  4. Statistics: Comprehensive benchmark and threading information storage

function convertdata(output::Int; datatypes::Array{<:Any,1}=[missing], path::String="./", fpath::String="./", fname = "output", compress::Any=nothing, comments::Any=nothing, lmax::Union{Int, Missing}=missing, xrange::Array{<:Any,1}=[missing, missing], yrange::Array{<:Any,1}=[missing, missing], zrange::Array{<:Any,1}=[missing, missing], center::CenterType=[0., 0., 0.], rangeunit::Symbol=:standard, smallr::Real=0., smallc::Real=0., verbose::Bool=true, showprogress::Bool=true, maxthreads::Int=Threads.nthreads(), myargs::ArgumentsType=ArgumentsType() )

return statistics_dictionary

Arguments

Required:

  • output: RAMSES output number to convert

Optional Keywords:

  • datatypes: Array of datatypes to convert.
    • Default: [missing] → converts all available data (:hydro, :gravity, :particles, :clumps, :rt, :sinks)
    • Examples: [:hydro, :particles], [:hydro], :particles
  • path: Path to RAMSES simulation folders (default: "./").
  • fpath: Output path for JLD2 files (default: "./")
  • fname: Base filename for output files (default: "output_")
    • Final filename: fname + output_number + ".jld2"
  • compress: Compression settings
    • Default: nothing → automatic LZ4 compression
    • Options: false (no compression), LZ4FrameCompressor(), Bzip2Compressor(), ZlibCompressor()
    • Requires: CodecZlib, CodecBzip2, or CodecLz4 packages for specific compressors
  • comments: String description of the simulation (stored in file metadata)
  • lmax: Maximum AMR level to process
    • Default: missing → uses all available levels
    • Limits data processing to specified refinement level
  • xrange, yrange, zrange: Spatial selection ranges [min, max]
    • Default: [missing, missing] → full simulation box
    • Units specified by range_unit, relative to center
    • Zero-length ranges (min=max=0) converted to maximum extent
  • center: Coordinate center for spatial ranges
    • Default: [0., 0., 0.] → simulation origin
    • Special values: [:bc], [:boxcenter] → box center
    • Mixed: [value, :bc, :bc] → custom center per axis
  • range_unit: Units for spatial ranges and center
    • Options: :standard (code units), :Mpc, :kpc, :pc, :mpc, :ly, :au, :km, :cm
    • See viewfields(info.scale) for available unit conversions
  • smallr: Lower density threshold (0 = inactive)
  • smallc: Lower thermal pressure threshold (0 = inactive)
  • max_threads: Threading control for data loading operations
    • Default: Threads.nthreads() → uses all available Julia threads
    • Applied to: :hydro, :gravity, :particles data loading
    • NOT applied to: :clumps and :sinks data (single-threaded)
    • Examples: max_threads=4 (limit to 4 threads), max_threads=1 (single-threaded)
  • verbose: Enable detailed console output (default: true)
  • show_progress: Enable progress bars during data loading (default: true)
  • myargs: Pre-configured ArgumentsType struct to override multiple parameters

Return Value:

Returns a comprehensive statistics dictionary containing:

  • TimerOutputs: Detailed timing for reading/writing operations
  • threading: Threading configuration and system information
  • benchmark: Performance metrics, compression ratios, processing times
  • viewdata: Metadata about the converted dataset
  • size: Memory usage and file size information

Method Overloads:

  • convertdata(output::Int64; ...) → Full parameter interface
  • convertdata(output::Int64, datatypes::Vector{Symbol}; ...) → Direct datatype specification
  • convertdata(output::Int64, datatypes::Symbol; ...) → Single datatype conversion

Threading Behavior:

  • Threaded operations: File-level parallelism for :hydro, :gravity, :particles
  • Single-threaded: :clumps and :sinks data processing (threading not beneficial)
  • Thread safety: All operations use thread-safe file I/O and memory management
  • Performance: Optimal threading automatically balances CPU files across threads

Usage Examples:

Convert all datatypes with default settings and available threads

stats = convertdata(42, path, fpath)

Convert specific datatypes with threading control

stats = convertdata(42, [:hydro, :particles], path="source/folder", fpath="export/folder", max_threads=4)

Spatial selection with different compression

stats = convertdata(42, xrange=[-10, 10], yrange=[-10, 10], rangeunit=:Mpc, compress=Bzip2Compressor(), maxthreads=8)

Access performance statistics println("Total time: ", stats["benchmark"]["totalprocessingtimeseconds"]) println("Compression ratio: ", stats["benchmark"]["compressionratio"]) println("Threads used: ", stats["threading"]["effective_threads"])

Mera.batch_convert_mera — Function
batch_convert_mera(input_dir::String, output_dir::String,

Required Parameters

  • input_dir: Source directory containing old JLD2 files with version issues
  • output_dir: Destination directory for converted files (created if doesn't exist)
  • start_output: Starting output number for conversion range (inclusive)
  • end_output: Ending output number for conversion range (inclusive)

Performance Tuning Parameters

  • requested_threads: Desired number of conversion threads (default: all available)
  • safety_margin: Memory usage threshold as decimal 0.0-1.0 (default: 0.8 = 80%)
  • min_threads: Minimum thread count even under resource constraints (default: 1)
  • max_threads: Maximum thread count regardless of system capacity (default: 64)

Behavior Control Parameters

  • skip_existing: Skip files that already exist in output directory (default: true)
  • show_confirmation: Display user confirmation prompt before starting (default: true)
  • compress: Compression codec for the output files, matching savedata's API (default: nothing → LZ4FrameCompressor()). Pass false to write uncompressed files, or a specific codec instance (LZ4FrameCompressor(), ZlibCompressor(), Bzip2Compressor()) for finer control.
  • sidecar: also write <file>.meta.json next to each converted file, as savedata does: the data types it holds, the provenance of the snapshot, the environment, and the file it was converted from (default: true). The global switch sidecar overrides it.

Safety Margin System

The safety_margin parameter is now actively used throughout the process:

Pre-Conversion Phase

  • Validates current system memory usage
  • Adjusts thread recommendations based on available memory within safety limits
  • Warns user if current usage already exceeds margin

During Conversion Phase

  • Monitors memory usage before each file load operation
  • Checks memory after data loading (peak usage point)
  • Triggers automatic garbage collection on violations
  • Counts total violations for reporting

Post-Conversion Phase

  • Reports final memory state and violation statistics
  • Provides recommendations for future conversions based on violation patterns

Return Value

Returns comprehensive dictionary with conversion statistics:

  • success: Number of files successfully converted
  • failed: Number of files that failed conversion
  • skipped: Number of files skipped (already existed)
  • safety_violations: Number of times memory exceeded safety margin
  • conversion_time: Total time spent in conversion (seconds)
  • threads_used: Actual number of threads used
  • final_memory_usage_percent: Memory usage percentage at completion

Error Handling Strategy

The function handles errors gracefully:

  • Individual file failures don't stop the batch
  • Out-of-memory errors receive specific guidance
  • System resource violations trigger automatic recovery
  • All errors are logged with specific context

Example Usage

Basic conversion with default safety settings: results = batchconvertmera("/data/old", "/data/new", 100, 200)

Conservative conversion for large files: results = batchconvertmera("/data/old", "/data/new", 100, 200; requestedthreads=4, safetymargin=0.9)

High-performance conversion with monitoring: results = batchconvertmera("/data/old", "/data/new", 100, 200; requestedthreads=16, safetymargin=0.7, skip_existing=false)

I/O tuning

Reading large outputs is usually I/O bound, so Mera exposes its buffer and cache settings. Most users never need these, optimize_mera_io picks settings for a given simulation and is the one entry point worth knowing.

Mera.optimize_mera_io — Function
optimize_mera_io(simulation_path::String, output_num::Int; benchmark=false, quiet=false)

Automatically optimize Mera I/O settings based on your simulation characteristics.

This is the easiest way to get optimal performance - just provide your simulation path and output number, and Mera will analyze your data and apply the best settings.

Arguments

  • simulation_path: Path to your RAMSES simulation directory
  • output_num: Output number to analyze (e.g., 300)
  • benchmark=false: Set to true to run performance benchmarks for fine-tuning
  • quiet=false: Set to true to suppress output messages

Returns

  • true if optimization was successful, false otherwise

Examples

# Basic automatic optimization
optimize_mera_io("/Volumes/Storage/Simulations/mw_L10", 300)

# With benchmarking for maximum performance
optimize_mera_io("/Volumes/Storage/Simulations/mw_L10", 300, benchmark=true)

# Quiet mode for scripts
optimize_mera_io("/path/to/sim", 300, quiet=true)

What it does

  1. Analyzes your simulation (file count, sizes, AMR structure)
  2. Recommends optimal buffer size based on simulation characteristics
  3. Enables file metadata caching for faster repeat operations
  4. Optionally benchmarks different settings to find the absolute best performance

Simulation size recommendations

  • Small (< 50 files): 32KB buffer
  • Medium (50-200 files): 64KB buffer
  • Large (200-500 files): 128KB buffer
  • Very large (500-1000 files): 256KB buffer
  • Huge (> 1000 files): 512KB buffer
