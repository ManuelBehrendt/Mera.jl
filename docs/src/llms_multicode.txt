
## The multicode build: other simulation codes

This part applies to the `multicode` branch (Mera 2.0.0-DEV, installed with
`] add https://github.com/ManuelBehrendt/Mera.jl#multicode`). It replaces two statements above:
here `getinfo` is not RAMSES-only, and Mera reads more than RAMSES. Everything else above holds for
every code.

**Codes read:** RAMSES, PLUTO (static grid), Chombo (PLUTO-AMR, ORION2 and other Chombo-format
HDF5), Athena++ (`.athdf`), FLASH (PARAMESH HDF5), GADGET (HDF5 and GADGET-2 binary), AREPO
(including IllustrisTNG) and AMReX/Quokka plotfiles. These readers are tested on format fixtures
and a few real runs, far fewer than the RAMSES one: check a first result against a tool you trust.

    info = getinfo(5, "/path/to/run")          # the code is detected from the files; code=:pluto overrides
    info.simcode                               # "PLUTO", "CHOMBO", "Athena++", "FLASH", "GADGET", "AREPO", ...
    gas  = gethydro(info)                      # grid codes: RAMSES, PLUTO, Chombo, Athena++, FLASH, AMReX
    gas  = getparticles(info; families=[0])    # GADGET and AREPO: the gas is particle data
    capabilities(info); supports(info, :gravity)

Every reader returns the same objects (`HydroDataType` for cells, `PartDataType` for particles) with
the same columns, units and cell convention, so every function and every tutorial applies unchanged.

### Traps on the other codes

1. **Only RAMSES has `getgravity`, `getrt` and `getclumps`.** Other codes keep the potential and the
   radiation inside the snapshot; the readers map them to canonical columns of the gas: `:gpot`
   (Athena++ `phi`, FLASH `gpot`, Chombo `gravitational-potential`), the fractions `:xHI`, `:xH2`,
   `:xCO`, `:xHII`, ... and the photon groups `:Np1...:Np8`. Ask `supports(info, :gravity)` before
   calling a getter; an unsupported call fails with a message naming what the code does have.
2. **Most formats store no physical units.** PLUTO and Athena++ data, and a bare AMReX plotfile,
   load in code units (`unit_* = 1`). Pass the run's CGS units to `getinfo`:
   `getinfo(5, path; unit_length=3.086e21, unit_density=1.67e-24, unit_velocity=1e5)`. FLASH is
   read as CGS, a Quokka plotfile takes its units from `metadata.yaml`, GADGET and AREPO from the
   header, or GADGET's defaults (1 kpc/h, 1e10 Msol/h, 1 km/s, with a printed note) when the header
   has none. A unit symbol such as `:kpc` on code-unit data gives a number, but not a physical one.
3. **No format records the composition.** `:nH` and `:T` use X = 0.76 and μ = 1.32 (the RAMSES
   convention) unless the reader knows better; `getinfo` prints what it uses. Change it with
   `setcomposition!(info; X_frac=..., mu=...)`.
4. **GADGET and AREPO gas is particles.** Load it with `getparticles(info; families=[0])`, not
   `gethydro`. AREPO cells carry `:volume`; project them with `weighting=:voronoi` or `:sph`.
   `getgroups` reads the FoF/SUBFIND catalogue (subhalos are not read), `getlogs` the run-time logs.
5. **Chombo is a format, not a code.** The file does not say which code wrote it. Mera decides it
   as yt does: `pluto.ini` next to the file means PLUTO-AMR, `orion2.ini` or a `CeilVA_mass`
   attribute means ORION2.

### Sidecars, records and citations on every code

The (1.9) record on disk works the same on every reader: `exportdata` and `savedata` write
sidecars, `readsidecar` verifies them, and `bundle`, `citation`, `simulationrecord` and `datacite`
work on any `info` or data object.

- **Input files.** A sidecar records the SHA-256 of the files that define the run, looked up next
  to the snapshot and one folder up: RAMSES `namelist.txt` and the build files, PLUTO `pluto.ini`
  and `definitions.h`, Chombo also `orion2.ini`, Athena++ `athinput.*`, FLASH `flash.par` and the
  setup files, AMReX `job_info` and Quokka `metadata.yaml`, GADGET/AREPO `parameters-usedvalues`,
  `param.txt` and `Config.sh`. A file that is not there is skipped.
- **Physics.** `simulationrecord(info)["physics"]["summary"]` has the same keys on every code:
  `hydro`, `mhd`, `gravity`, `particles`, `radiative_transfer`, `cooling`, `star_formation`,
  `feedback`, `sinks`. Each is `false`, `true`, the settings of that process, or `nothing` when the
  output does not say, and `nothing` is common: do not read it as `false`. The parameters it came
  from sit next to the summary: PLUTO `definitions.h` and `pluto.ini`, the components of a Chombo
  file, the Athena++ input blocks, FLASH's runtime parameters and setup call stored in the file,
  AMReX `job_info`, and AREPO's or GADGET-4's `Config` and `Parameters` groups.
- **Whole runs.** `simulationrecord("/path/to/run")` lists every output of any code with its time
  and size, from the reader's own list of outputs; `timeseries` and `getmovie` use the same list.
  Codes without a grid (GADGET, AREPO) report no refinement levels.
- **What to cite.** `citation(info)` gives Mera at its version and the code paper: PLUTO, Athena++,
  FLASH, Quokka, AMReX, AREPO, SWIFT, GIZMO. GADGET lists both the GADGET-2 and the GADGET-4 paper,
  because the files do not say which wrote them; keep the one that applies. A Chombo file cites the
  code that wrote it (PLUTO and PLUTO-AMR, or ORION2, with its sink-particle paper when a `.sink`
  file is there), and Mera alone when nothing says which.

More: https://manuelbehrendt.github.io/Mera.jl/multicode/multicode/ and the reader page of each code
in the sidebar of the multicode docs.
